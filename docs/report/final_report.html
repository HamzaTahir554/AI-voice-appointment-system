1. Executive Summary

Booking a doctor's appointment in Pakistan usually still means a phone call to a receptionist: the line is busy at peak hours, nobody answers after hours, and a receptionist juggling calls, walk-ins and paper diaries makes mistakes - double bookings, wrong days, missed cancellations. The AI Voice Appointment System automates that phone conversation. A patient speaks as they naturally would - English, Urdu, Roman Urdu, or a mixture such as “Mje docter ke pas jana h” - and the system works out what they want, asks only for what is missing, checks the doctor's real diary, and books, moves or cancels the appointment.

How it works. Speech is transcribed by ElevenLabs Scribe v2 Realtime. A fine-tuned multilingual BERT (mBERT) classifies each utterance into one of 31 intents (test accuracy 0.898, macro-F1 0.836 on 354 held-out sentences). A rule-based Dialogue Manager keeps the conversation state, fills the doctor/date/time slots, asks for confirmation and absorbs corrections. An Appointment Backend applies the clinic's rules and writes to Firebase Firestore inside a transaction, so a slot cannot be double-booked. Only then does a local language model (Ollama, llama3.2) phrase the reply; a response validator rejects any wording whose facts differ from the database, and the approved sentence is spoken by ElevenLabs streaming TTS.

Management. Doctors use a web Doctor Dashboard for their day's appointments, patients, weekly hours, leave, statistics and password. The clinic administrator uses a SuperAdmin Dashboard to add, edit, deactivate and remove doctors, set their usernames and passwords, manage leave, see and act on every appointment, edit the one clinic's details, and read clinic-wide and per-doctor statistics. It is a single-clinic system.

Status. Everything above is implemented and tested: 595 automated tests (582 passed, 13 live-service tests skipped, 0 failed) and 110 browser checks of the dashboards (all passed). Speech was measured against the real ElevenLabs service with synthetic callers: a caller who stops speaking hears the agent start after a median of 2.5 s (3.0-3.3 s in the microphone mode, where the language model words every reply). Not implemented: the telephone line itself (Asterisk/SIP) and the delivery of patient notifications. A real person speaking into the microphone has not yet been measured.

Main contribution. A complete, working appointment assistant for Pakistani Urdu and Roman Urdu speech in which the machine-learning components decide what the caller means and how the reply is worded, while every fact the caller hears and every change to the diary comes from deterministic, tested code and the database.

2. Introduction, Objectives and Scope

2.1 Background

Most clinics in Pakistan take appointments by telephone and keep them in a paper register or a spreadsheet. This causes familiar problems:

  • Phone dependency. Patients can book only while the line is staffed and free.
  • Receptionist workload. The same questions - fees, timings, location, “is the doctor in tomorrow?” - take up most calls.
  • Errors. Double bookings, wrong dates, and appointments that stay in the register after the patient cancelled.
  • Schedule changes. When a doctor is away, every affected patient has to be found and called by hand.
  • Waiting. Patients wait on hold, and wait at the clinic when bookings overlap.

Callers mix languages freely. The same request arrives as “I want an appointment”, “مجھے اپائنٹمنٹ چاہیے”, “Mujhe appointment chahiye” or “Mje docter ke pas jana h”, with non-standard Roman Urdu spelling that keyword systems and English-only models handle poorly.

2.2 Problem statement

Build a system that can hold an appointment conversation with a patient in English, Urdu, Roman Urdu or mixed speech; understand what they want even when it is phrased informally; collect the details it needs; apply the clinic's real schedule and rules without ever inventing availability or confirming something that did not happen; and give the clinic's doctors and administrator a way to manage the same data.

2.3 Proposed solution

A pipeline in which each stage has one job: speech-to-text produces the caller's words; mBERT classifies the intent; the Dialogue Manager decides the next step; the Appointment Backend performs any operation against Firestore; the LLM phrases the result; the validator checks the phrasing against the result; text-to-speech speaks it. Two web dashboards read and change the same Firestore data through the same backend rules.

4. System Architecture

4.1 The voice pipeline

One caller turn passes through every stage in order. The stages communicate by ordinary function calls inside one Python process, except for the three external services: ElevenLabs (STT over a WebSocket, TTS over HTTPS), Ollama (HTTP on the same machine) and Firestore (the Firebase Admin SDK).

4.2 Why the language model runs last

The language model is the only component that can make things up, so it is given no authority. By the time it runs, the appointment has already been booked or refused by deterministic code and the result is in Firestore. The model only chooses words, and the validator compares those words with the result: a time, date, doctor or appointment ID that is not in the result - or a claim of success after a failure - rejects the sentence, and the Dialogue Manager's own template is spoken instead. If Ollama is unavailable, the templates are used and the call continues.

4.3 Dashboard architecture

The browser never talks to Firebase and holds no credential or database address: it only calls the API with a session token. Writes that change appointments - booking, cancelling, moving, completing, leave - go through the same Appointment Backend as the voice assistant, so a doctor cannot bypass a rule the assistant has to follow. Because both paths use one Firestore database, a booking made by voice appears in the dashboard at its next 30-second refresh.

4.4 Single Clinic Architecture

The system serves exactly one clinic, configured by CLINIC_ID (default C001):

  • The clinic's name, address, city and phone are global. The assistant reads them to callers, every dashboard screen shows them, and only the SuperAdmin can change them (PATCH /admin/clinic). A doctor who tries to set a clinic field on their own profile is refused with 403 clinic_readonly.
  • A doctor added by the SuperAdmin belongs to the clinic automatically; there is no clinic selector anywhere, and doctor details show the clinic's name without it being entered.
  • There is no way to add a second clinic: the Clinic page shows one record, not a list (checked by the browser tests). Records left over from earlier multi-clinic test data can be merged into the one clinic with POST /admin/clinic/consolidate.
  • Multi-clinic support is not implemented and not planned in this project.

Status: Not implemented - future work. There is no Asterisk configuration, SIP account or telephony bridge in the project, and no telephone call has been made to the system.

What exists is the interface a bridge would use: a WebSocket endpoint, /voice/call (api/voice_ws.py), that accepts 8 kHz μ-law audio (or 16-bit PCM), runs the full pipeline and sends back the agent's audio plus stop_playback and hangup events. An Asterisk bridge (for example ARI External Media or AudioSocket) would forward the caller's audio to this socket and play what comes back; docs/VOICE.md section 5 describes what it must do.

6. Intent Detection – mBERT

6.1 Why mBERT

Callers mix English, Urdu script and Roman Urdu in one sentence and spell Roman Urdu freely (“mujhe”, “mje”, “mujhy”). Multilingual BERT (bert-base-multilingual-cased) was pre-trained on Wikipedia in 104 languages including Urdu and English, with one WordPiece vocabulary shared by all of them, so a single model can read all three forms. It is small enough to fine-tune on a 6 GB GPU and answers in about 8 ms per sentence on that GPU. The cased variant is used because the text is kept as the caller said it.

6.3 Preprocessing and tokenization

  1. Detect the text and intent columns of each file automatically (the four files use different schemas).
  2. Harvest parallel Urdu-script columns as extra samples.
  3. Map every raw label onto one 31-intent taxonomy.
  4. Normalise Unicode (NFKC) and whitespace only. No lower-casing, stop-word removal or stemming: mBERT is cased and a question mark is a real signal for question intents.
  5. Remove exact duplicates.
  6. Split 80/10/10, stratified by intent and grouped, so near-identical variants never straddle train and test: 2,760 train / 347 validation / 354 test, with 0 texts shared between train and test. Sentences that also appear in the evaluation sets were held out of training.

Tokenization uses mBERT's own WordPiece tokenizer with a maximum length of 64 tokens (padded/truncated), which covers a spoken sentence.

7. Dialogue Manager and Confidence Handling

mBERT answers “what does the caller want?”; the Dialogue Manager (dialog_manager/) answers “what should happen next?”. It is deterministic and never invents a fact: availability, fees, addresses and appointment IDs all come from the database.

7.1 Conversation state

Each session (one call or chat) keeps: the patient, the current intent and named dialogue state (idle, booking, confirmation, cancel, reschedule, status, doctor information, clarification), the slots collected so far, the slot being asked for, a pending intent (a question parked until a missing detail arrives), whether a yes/no confirmation is awaited, the reply language, and the last 40 turns. Sessions expire after 15 minutes of inactivity. Every message, with its intent and confidence, is logged to Firestore (conversation_sessions, conversation_messages).

7.2 One turn

  1. Perception: mBERT intent and confidence; rule-based entities; yes/no.
  2. A pending confirmation outranks everything: the caller is answering “shall I book it?”.
  3. Effective intent: chosen from the prediction and the context (7.4).
  4. Medium-confidence check: a guess that would start a new task with nothing to back it up is confirmed first (7.5).
  5. Intent switch: a confident new task abandons the old draft (bar 0.75).
  6. Slots: store what the caller said; a side question about another doctor does not change the doctor being booked.
  7. Dispatch to the handler, which asks for the next missing slot, asks for confirmation, or calls the backend.

7.3 Slot filling and entities

Entities are extracted by deterministic rules (validators.py), because “kal 4 baje” must always mean the same date and time: doctor names and their aliases in English and Urdu script; aaj, kal, parson, weekdays in English, Roman Urdu and Urdu, and calendar dates; times such as “4 baje”, “shaam 5”, “5 PM” and Urdu digits and number words, with a bare 1-8 o'clock read as afternoon (clinic hours); appointment IDs; phone numbers; names. All dates are resolved in Asia/Karachi time.

7.4 Context-aware decisions

  • Short answers continue the task. When the system asked “which day?” and the caller says “kal”, the model may predict anything; the date entity and the open booking decide.
  • Corrections: “nahi Dr Asim” replaces the doctor; the reply acknowledges it (“Theek hai ji”).
  • Draft edits: inside a booking, change_date/change_time/change_doctor edit the draft instead of starting a reschedule (which would ask for an appointment ID the caller does not have - seen in a live test).
  • Side questions: “Dr Ahmed ki fee kitni hai?” during a booking is answered, and the booking question is asked again in the same reply.
  • Moving one's own appointment: “Meri appointment Friday ko 5 baje kar dein” reads as a booking to mBERT; for a caller who has an upcoming appointment it is treated as a reschedule.
  • Confirmation: nothing is booked, moved or cancelled without an explicit yes; “ہاں، کر دیں” counts as yes even when mBERT reads it as change_date.
  • Clarification: after two failed attempts the assistant stops asking open questions and reads a short menu of what it can do.

The thresholds are configurable (HIGH_CONFIDENCE, CONFIDENCE_THRESHOLD, INTENT_SWITCH_THRESHOLD). Three rules run on the router's output:

  • Emergency safety net. Acute danger phrases (“saans nahi aa rahi”, “khoon beh raha hai”, “behosh”) escalate to emergency whatever the model said - added after the model read “Bohot khoon beh raha hai” as thank_you 0.97. The caller is told to call emergency services or go to the nearest hospital.
  • Booking corroboration. A low or medium guess is overridden to book_appointment only when the sentence has a subject (doctor, appointment), an action (jana, milna, chahiye…) and no competing vocabulary (fee, cancel, change, emergency…). It was written for “Mje docter ke pas jana h”, which an earlier model classified as change_doctor 0.41. The current model classifies it as book_appointment with confidence 1.00; the rule remains as a safety net.
  • Known confusions found in live calls: a farewell read as thanks, and availability asked in Urdu script.

8. Appointment Backend

The only code that creates or changes appointments (appointment_backend/). The voice assistant, the Doctor Dashboard and the SuperAdmin Dashboard all go through it. Every operation returns an OperationResult: success, the data the reply needs, or a precise error code.

8.1 Operations

OperationWhat it does

8.2 Validation gates (booking), in order

  1. The patient exists.
  2. The doctor exists and is active (a deactivated doctor cannot be booked).
  3. The clinic exists.
  4. The date is a real date and not in the past (Asia/Karachi).
  5. The time is a valid HH:MM.
  6. No duplicate: the same patient with the same doctor on the same day is refused.
  7. The doctor works that day, is not on leave, and the time is inside the working hours.
  8. The slot is free.
  9. The write re-checks the slot inside a Firestore transaction (reserve_slot): if someone took it between the check and the write, the booking fails with alternatives instead of creating a double booking.

Error codes: patient_not_found, doctor_not_found, clinic_not_found, invalid_date, date_in_past, invalid_time, duplicate_appointment, doctor_not_working, doctor_unavailable, outside_working_hours, slot_unavailable, appointment_not_found, not_your_appointment, already_cancelled, already_completed, backend_unavailable.

9.2 Read performance

The dashboards were measured to be slow on the live project (sign-in to a usable doctor dashboard: 7.3 s) and reworked (api/data.py, docs/PERFORMANCE.md):

  • Query filtering: screens read only their records (by doctor and date) instead of whole collections.
  • Batching: the patients on a page are fetched by ID in one call.
  • Counting without downloading: totals and statistics use Firestore count() aggregations.
  • Parallel reads inside a request; server-side paging by date.
  • Caching: the clinic record and the doctor register are cached in the API for one minute and dropped at once by any write through the API; appointments, patients and notifications are never cached, and the booking rules never read the cache.
  • Indexes: four composite indexes are declared in firestore.indexes.json. They have not been deployed to the live project; until they are, each query that needs one falls back to a simpler query plus filtering, with the same result.

Measured on the live project (median of three runs): doctor sign-in to a usable dashboard 7.3 s → 1.2 s; the 30-second refresh 3.4 s → 0.57 s (4 requests → 1); administrator overview 5.7 s → 1.7 s; every page once 40.8 s → 12.0 s. On a simulated clinic of 20,000 appointments the same pages read 9,240 documents instead of 157,429. From this machine one Firestore round trip takes about 0.55 s, and for long stretches about 2.35 s - network latency outside the application.

10.3 Hallucination prevention - the validator

The prompt asks the model not to invent facts; the validator enforces it. A generated sentence is rejected when:

  • it mentions a time, date or appointment ID that is not in the backend result (“4 baje” is accepted for 16:00; “17 baje” is rejected as unnatural Urdu);
  • it says kal, a weekday or a day of the month that is not the backend's date;
  • it claims success (“booked”, “ho gayi”, “cancel kar di”) when the operation failed;
  • it reads out a raw ISO date, is too long for speech, or is in the wrong language;
  • (rewording) it adds or drops a number, time, day or doctor, adds or removes a “nahi”, drops the question the caller must answer or asks a new one, claims something was done, or turns the sentence onto the receptionist herself.

On rejection, on a missing or empty answer, or if Ollama is down, the Dialogue Manager's template for the turn is spoken - in English, Roman Urdu or Urdu. The call never waits on or breaks because of the model.

17. Limitations and Future Work

17.1 Limitations

  • No telephone line. Asterisk/SIP is not implemented; the system is reached by microphone, WebSocket or text.
  • Speech not tested with real people. All speech measurements used synthetic callers (ElevenLabs voices), which mis-heard Urdu time words (“kal” → “Cole”, “kal ke liye” → “Calcutta”). Noise, accents and real microphones are untested.
  • Voice. On the free ElevenLabs plan only built-in voices work through the API; the agent's voice is an English voice speaking Urdu, and its pronunciation has not been judged by a listener. Speech needs an internet connection and costs credits per use.
  • Intent model. Most of the corpus (2,374 of 3,461 sentences) is generated; several intents have fewer than ten test sentences; goodbye, clinic timing, help and repeat are weak; there is no out-of-scope class (“Aaj mausam kaisa hai?” is answered with clinic information).
  • Language detection misses very informal Roman Urdu (“Mje docter ke pas jana h” was answered in English with the reply language on automatic).
  • Language model. llama3.2 (3B) wording was used for 3 of 21 booking results and for 13-15 of 18 other replies in two runs; the validator checks facts, not grammar; it adds about 0.5-1 s per reply and occasionally several seconds.
  • Notifications are queued but not delivered (no SMS or call provider).
  • Firestore latency from the development network is 0.55-2.35 s per round trip, the composite indexes are not deployed, and a voice turn against live Firestore has not been measured.
  • Rescheduling re-checks the slot and then updates the record, but not inside a transaction, unlike a new booking.
  • Authentication is a prototype: in-process sessions, no rate limiting, unauthenticated dialogue routes.
  • Microphone mode through loudspeakers cannot be interrupted (the microphone is muted while the agent speaks).
  • The text console (voice_pipeline.py) re-writes the demo doctors, schedules and patients into the configured database when it starts; against Firestore that overwrites dashboard edits to those records.

17.2 Future work

  • An Asterisk bridge (ARI External Media or AudioSocket) to the existing /voice/call endpoint, and tests over a real phone line.
  • Testing with real patients' speech and recordings; an Urdu-native voice (a paid ElevenLabs plan).
  • More natural training sentences per intent, a fresh held-out set, and an out-of-scope class.
  • A stronger local model (for example qwen2.5:7b, which fits the 6 GB GPU) for better Roman Urdu wording.
  • An SMS or voice-call provider behind the existing NotificationSender interface.
  • Firebase Authentication and rate limiting; deploying the declared Firestore indexes; a transactional reschedule; fewer sequential Firestore reads in the booking path.
  • A mobile-friendly dashboard application, richer analytics, and a production deployment (hosting, HTTPS, monitoring).

18. Conclusion

The project delivers a working AI appointment assistant for a single clinic. A patient can book, check, reschedule and cancel an appointment by speaking English, Urdu, Roman Urdu or a mix, through the computer's microphone and speaker today and through a telephone bridge once one is connected to the existing call endpoint. The same conversation works over text.

The main AI contributions are a fine-tuned mBERT classifier for 31 intents in mixed-script Pakistani speech (accuracy 0.898, macro-F1 0.836 on clean held-out data), a context-aware Dialogue Manager that keeps a conversation on track even when single words are misclassified, and a design in which a local language model improves the wording of replies while a validator guarantees that every fact the patient hears comes from the database. Appointment automation is deterministic and safe: validation gates, transactional booking, alternatives when a slot is taken, and a doctor-leave cascade that cancels and records notifications for every affected patient.

Doctors manage their own day, and the administrator manages the doctors, their credentials and leave, every appointment and the clinic itself, with role rules enforced on the server and statistics computed from real records. The system is tested by 595 automated tests and 110 browser checks with no failures.

It is ready for demonstration and supervised trials. Before real patients can rely on it by telephone, it needs the Asterisk/SIP bridge, testing with real callers, delivery of patient notifications and production-grade authentication.
