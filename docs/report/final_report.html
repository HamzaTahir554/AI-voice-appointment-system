1. Introduction

1.1 Project title

AI Voice Appointment System – a multilingual conversational assistant for booking doctor appointments at a clinic in Pakistan.

1.2 Background

Most clinics in Pakistan take appointments by telephone. A receptionist answers, checks the doctor's diary by hand or in a spreadsheet, and writes the booking down. Patients speak Urdu, English, or – very often – Roman Urdu mixed with English words ("Mujhe Dr Ahmed se kal 4 baje appointment chahiye"). Staff time is limited, calls are missed outside opening hours, and double bookings and lost cancellations are common.

1.3 Problem statement

Appointment handling needs to understand what a patient wants in the languages they actually use, apply the clinic's scheduling rules consistently, and keep doctors and clinic staff informed – without a person having to transcribe every request.

1.4 Proposed solution

A conversational pipeline that takes what the patient says, classifies their intent with a fine-tuned multilingual BERT model, runs a stateful dialogue to collect the doctor, date and time, applies the clinic's rules in a dedicated appointment backend, stores everything in Firebase Firestore, and phrases the reply with a local large language model that is prevented from changing any fact. Doctors manage their own day through a web dashboard; a clinic administrator manages the doctors, the clinic and every appointment through a separate administration area.

1.5 Motivation

  • Serve patients in their own language, including Roman Urdu and code-mixed speech that off-the-shelf English systems handle poorly.
  • Keep the rules deterministic: a language model is good at wording and bad at being trusted with a diary, so the booking logic is ordinary tested code.
  • Give doctors and the clinic an accurate, shared view of the diary, whether an appointment was made through the assistant or on the dashboard.
Scope note. The design targets telephone calls (Asterisk/SIP, speech recognition and speech synthesis). Those three stages are not implemented in this repository. The implemented pipeline takes the patient's words as text and returns the reply as text; Sections 12–14 describe the exact state of each.

2. Objectives

The objectives below are the ones the implemented system meets.

  1. Understand multilingual requests. Classify a patient's utterance into one of 31 intents in English, Urdu (Arabic script), Roman Urdu or a mixture, using a fine-tuned mBERT model.
  2. Hold a real conversation. Track what has been said across turns, ask only for missing information, confirm before acting, and recover from corrections and unclear input.
  3. Enforce clinic rules in one place. Book, cancel and reschedule only through a backend that validates dates, working hours, doctor availability and double bookings.
  4. Persist reliably. Store patients, doctors, the clinic, schedules, appointments, conversations and notifications in Firebase Firestore, with an in-memory stand-in for offline development and tests.
  5. Word replies naturally but safely. Use a local LLM through Ollama to phrase replies, and reject any wording that contradicts the backend's result.
  6. Serve the doctors. Give each doctor a dashboard for their own appointments, patients, working hours, leave, profile, notifications and statistics.
  7. Serve the clinic. Give a single administrator control of the one clinic, every doctor, their sign-in credentials, their leave, every appointment and clinic-wide statistics.
  8. Protect access. Separate the two roles on the server, keep credentials out of source code and the browser, and hash stored passwords.

3. System Overview

The intended end-to-end flow, and what exists today:

3.1 One conversation turn, as implemented

  1. The patient's words arrive as text at POST /dialog/message (or /voice/message, or the interactive voice_pipeline.py).
  2. The intent router runs the fine-tuned mBERT classifier and returns an intent and a confidence.
  3. The Dialogue Manager updates the session state, extracts entities (doctor, date, time, appointment ID, patient details), and decides the next action: ask for a missing slot, check availability, ask for confirmation, or act.
  4. Only after confirmation does it call the Appointment Backend, which validates the request and reads or writes Firestore.
  5. The backend's result goes to the Ollama judge, which phrases a reply in the caller's language. The response validator rejects any wording whose times, dates or IDs differ from the result, in which case a deterministic template is used instead.
  6. The reply is returned as text, together with the intent, confidence, action and slot state.

Every appointment written this way appears in the doctor's dashboard and the administrator's views, because both read the same Firestore collections through the same backend.

4. System Architecture

The system is one Python code base served by a single FastAPI process, plus a static web front end served by that process at /ui. There is one backend: the voice pipeline and both dashboards call the same Appointment Backend and the same Firestore data layer.

4.1 How the components communicate

  • In-process calls. Within the API process, the Dialogue Manager calls the intent router, the Appointment Backend and the Ollama judge as ordinary Python objects.
  • HTTP to Ollama. The judge calls the local Ollama server's REST API with httpx (default http://localhost:11434).
  • Firebase Admin SDK. The firebase/ repository talks to Firestore with the server-side Admin SDK. The browser never talks to Firebase directly.
  • HTTP from the browser. The dashboards call /auth/*, /dashboard/* and /admin/* with a bearer token; every call is scoped on the server to the signed-in role.
  • One result shape. Every backend operation returns an OperationResult (success, operation, appointment_id, status, data, error), which the API maps to HTTP status codes (404, 403, 400, 409, 503).

4.2 Why the language model is last

By the time the LLM runs, the appointment has already been booked, refused or looked up by deterministic code. The LLM can only change the wording; the validator checks the wording against the result. The worst case when the model misbehaves is a plainer sentence, never a wrong booking.

Emergency safety net. Because the model misses some emergencies phrased in ways it has not seen, the Dialogue Manager also escalates acute-danger phrases (for example chest pain, heavy bleeding, breathlessness) regardless of the predicted intent, with stand-down rules for routine mentions such as "test" or "checkup". 6. Dialogue Manager

The Dialogue Manager (dialog_manager/) turns a sequence of intents into a finished task. It is deterministic code, not a language model.

ModuleResponsibility
dialog_manager.pyThe conversation controller: routes each turn, chooses the next action, calls the backend.
intent_router.pyLoads the mBERT model and applies the confidence bands.
state_manager.pyPer-session state, persisted in conversation_sessions; sessions expire after 15 minutes of silence.
slot_manager.pyWhich slots each workflow needs (doctor, date, time, appointment ID, patient details) and which are still missing.
validators.pyEntity extraction and validation: doctor names and aliases, relative and absolute dates, spoken times, phone numbers, appointment IDs.
semantic_fallback.pyCorroborates low- and medium-confidence intents; also hosts the emergency safety net.
responses.pyTurns a decision into words, in the caller's language.

6.1 Conversation management

Each turn is processed against the session's state: the active workflow, the filled slots, any pending confirmation and the language the caller is using. Every message is stored in conversation_messages (phone numbers masked), and GET /dialog/transcript/{session_id} returns a call's transcript.

6.2 Intent handling

The router's intent selects a workflow (book, cancel, reschedule, check status, availability, doctor or clinic information, patient details, conversation). Side questions asked in the middle of a booking ("what is Dr Ahmed's fee?") are answered and the booking then resumes. Correction intents (change_date, change_time, change_doctor) are absorbed into the current booking instead of starting a new one.

6.3 Slot and entity handling

  • Doctor: matched against the name and aliases stored on each doctor record, longest alias first; an ambiguous name ("Dr Hamza" when two doctors share it) is asked about rather than guessed. A replacement ("Dr Ahmed nahi, Dr Asim") replaces the earlier choice.
  • Date: relative dates (kal, parson, today, tomorrow), weekday names, and day-of-month forms, resolved in the Asia/Karachi time zone.
  • Time: spoken forms such as "shaam 5 baje" or "4:30 PM".
  • Appointment ID and patient details: extracted when a workflow needs them.

6.4 Confirmation, clarification and the booking flow

greeting -> book_appointment
  -> ASK_FOR_DOCTOR -> ASK_FOR_DATE -> ASK_FOR_TIME   (only the missing slots)
  -> CHECK_AVAILABILITY (backend dry run)
       free:     ASK_CONFIRMATION -> "haan" -> CREATE_APPOINTMENT -> reply with ID
       not free: OFFER_ALTERNATIVES (nearest free slots)
  -> deny at confirmation: nothing is written; the caller can change a slot

The actions the manager can take are defined in config.Action: asking for each slot, checking availability, asking for confirmation, creating, cancelling and rescheduling appointments, checking status, giving doctor and clinic information, offering alternatives, greeting, clarifying, escalating an emergency, and ending the conversation.

6.5 Error handling

  • Backend failures come back as a structured result and are explained to the caller in plain words; technical errors are never read out.
  • If the database is unreachable the assistant says so instead of pretending to book.
  • Dead ends found in testing are closed: for example, answering "nahi" to "what is your appointment ID?" lists the caller's bookings instead of looping.

7. LLM Judge and Response Generator

7.1 Why an LLM is used

Template replies are correct but stiff, and do not adapt to the caller's wording. A local LLM rephrases the backend's result naturally. Running it locally through Ollama keeps patient data on the clinic's machine and costs nothing per call.

7.2 Model and settings

SettingValue
RuntimeOllama (tested with version 0.34.4), called over HTTP with httpx
Modelllama3.2 (OLLAMA_MODEL)
Temperature0.2 – it rewrites facts it is given, it does not invent
Maximum tokens200 – a spoken reply is one or two sentences
Timeout30 s, after which the template is used

7.3 Judge, validation and decision process

backend result -> Ollama (prompt with the facts) -> response validator -> approved text
                                                            |
                                                            +-- rejected -> deterministic template

The validator (response_validator.py) checks every time, date and appointment ID mentioned in the generated sentence against the backend result, rejects a failed operation described as a success, and rejects wrong relative dates, wrong weekdays, raw ISO dates, and a reply in the wrong language or script. If anything fails, the deterministic template (fallback.py, dialog_templates.py) is used.

7.4 Languages

Replies are produced in English, Roman Urdu or Urdu (language.py), following the caller's language unless RESPONSE_LANGUAGE fixes it. Templates exist for every action in all three languages, so the assistant answers in the caller's language even with the LLM switched off.

7.5 Integration with the Dialogue Manager

The Dialogue Manager decides what happens and the backend makes it happen; only then is the judge asked how to say it. Turns with no database operation (a slot question, a greeting) use templates by default, because there is no backend result to validate the model's wording against (OLLAMA_TRANSLATE turns that on for stronger models).

Measured behaviour. In the recorded live run against llama3.2 (reports/ollama_live.json), 21 replies were requested: 3 were accepted by the validator and 18 fell back to templates, with a median latency of 4.12 s. An earlier run recorded 9 of 21 accepted. The guard is doing its job – the small 3-billion-parameter model often mangles Roman Urdu or restates a time differently – and the templates carry most calls. A larger model would raise the acceptance rate.

8.3 Business rules

  • Valid date and time: no past dates; the time must be one of the doctor's slots for that weekday.
  • Doctor must be active: a deactivated or removed doctor is refused and is not offered to callers.
  • Doctor must be working: the weekly schedule (schedules) and leave dates (doctor_unavailability) are applied; the seeded clinic closes on Sunday.
  • No double booking: availability is checked, then the write goes through a transactional reserve_slot that re-checks inside a Firestore transaction, so two callers racing for the same slot cannot both win.
  • Ownership: a caller may only cancel or move their own appointment; a doctor may only act on appointments in their own diary.
  • Final states are final: a completed or cancelled appointment cannot be changed again.

8.4 Doctor leave

Blocking a date runs one cascade: the date is written to doctor_unavailability (so new bookings are refused), every live appointment that day becomes cancelled_by_doctor, and one notification per affected patient is queued in notifications. The administrator sees a preview of exactly which appointments and patients will be affected before confirming. Re-opening the date accepts new bookings but does not resurrect the cancelled ones.

9.5 Authentication to Firebase

The server authenticates with a service account, given either as three environment variables (FIREBASE_PROJECT_ID, FIREBASE_CLIENT_EMAIL, FIREBASE_PRIVATE_KEY) or as the path to the key file (FIREBASE_CREDENTIALS_FILE). scripts/verify_firebase.py checks the configuration and connectivity. No Firestore security-rules file is part of this repository; all access is from the server's Admin SDK.

12. Speech-to-Text (STT)

Status: not implemented. There is no speech-recognition component in this repository. No module converts audio to text, and no test exercises one. The recorded performance measurements list speech-to-text as "not measured: no STT integration exists in the codebase".

What exists instead. The pipeline accepts the patient's words as text at POST /dialog/message, POST /voice/message and in the interactive voice_pipeline.py. Everything downstream – intent detection, dialogue, backend, database, reply – works on that text, so an STT stage can be added in front without changing it.

Language support that would apply. The text stages already handle English, Urdu in Arabic script, Roman Urdu and mixed input (Section 5.2), so an STT model's output in any of those forms can be consumed directly.

Considerations for adding it (future work): telephone audio is 8 kHz narrow-band (G.711 μ-law or A-law); recognition latency adds directly to each turn; and an Urdu-capable model such as Whisper would be needed.

13. Text-to-Speech (TTS)

Status: not implemented. There is no speech-synthesis component in this repository.

The reply is produced as text in English, Roman Urdu or Urdu (Section 7.4), returned by /dialog/message and /voice/message. Dates and times are already written in spoken form (for example "Thursday, 1 October at 6:00 PM", never an ISO date), so a TTS engine can read the text as it is. Adding TTS is future work.

14. Asterisk / SIP Telephony

Status: not implemented. There is no Asterisk configuration, dial plan, SIP account, AudioSocket or AGI integration in this repository.

The integration point that exists. POST /voice/message is designed as the endpoint a telephony layer would call on each turn: it takes a session ID, the transcribed text and an optional patient ID, runs the whole pipeline, and returns the sentence to speak together with the intent, the backend result and the judge's decision. A future telephony bridge would connect Asterisk (receiving the call), an STT stage, this endpoint and a TTS stage.

The caller would be identified by phone number (PatientService.find_by_phone exists and is used today); in production the caller ID from the telephony layer would supply it.

16. Security

16.1 Secrets and environment variables

  • All secrets come from environment variables or a .env file that is ignored by Git. .env.example lists the variable names with empty values.
  • The Firebase service-account file is ignored by Git by name pattern, and every other JSON file is ignored unless explicitly listed.
  • The browser holds no Firebase credential, API key or server address; the dashboard never displays configuration or connection details.
  • A test (tests/test_security.py) scans the source, the reports and this PDF for private keys and service-account e-mail addresses, and checks that the secret files are ignored.

16.2 Authentication

  • POST /auth/login accepts a username, a doctor ID or the administrator ID, and returns an opaque random token (secrets.token_urlsafe(32)) sent as a bearer token.
  • Passwords are stored in dashboard_accounts as PBKDF2-HMAC-SHA256 hashes (120,000 iterations, a 16-byte random salt per account) and compared in constant time. No password or hash is ever returned by the API.
  • DASHBOARD_PASSWORD and SUPERADMIN_PASSWORD are only starting passwords: they open an account that has never had one set, and stop working as soon as one is.
  • Wrong ID and wrong password give the same answer, so the sign-in form cannot be used to discover valid IDs. A deactivated doctor cannot sign in.

16.3 Authorisation

  • Two roles, enforced on the server: doctor for /dashboard/* and superadmin for /admin/*. Each is refused (403) by the other's routes.
  • A doctor's routes take the doctor ID from the session, never from the request; another doctor's appointment returns 403.
  • A doctor cannot change their username, the clinic's details or anyone else's credentials; there is no route for the first and the API refuses the others.
  • Changing a password signs the account out of its other sessions.

16.4 API and Firebase security

  • CORS is limited to the origins in DASHBOARD_ORIGINS, without credentials.
  • Firestore is reached only by the server's Admin SDK.
Known limits. Sessions live in the API process, so restarting it signs everyone out; there is no sign-in rate limiting and no self-service password reset. The public voice-pipeline routes (/appointments/*, /dialog/*, /voice/message) are not authenticated, because they are meant to sit behind the telephony layer on a private network. Production would add Firebase Authentication and network restrictions.

20. Conclusion

The implemented system understands appointment requests in English, Urdu, Roman Urdu and mixed speech with a fine-tuned mBERT classifier (test accuracy 0.898, macro-F1 0.836 over 31 intents), holds a stateful conversation that asks only for what is missing and confirms before acting, applies the clinic's scheduling rules in a single tested backend, and stores everything in Firebase Firestore. A local language model phrases replies naturally but is never allowed to change a fact.

Around that pipeline, doctors have a dashboard for their own day, and a single administrator manages the one clinic, its doctors, their credentials, their leave, every appointment and clinic-wide statistics, with the separation between the two roles enforced on the server. The system is covered by 470 automated tests, of which none fail, and 110 browser checks.

The telephone layer – Asterisk/SIP, speech recognition and speech synthesis – remains future work. The pipeline was built so that these stages attach at its two ends without changes to the parts described in this report.
